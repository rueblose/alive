## Missing Files Center — ПОКА В ПЛАНАХ. НА ДАЛЕКОЕ БУДУЩЕЕ

Это должно быть отдельное окно, а не попытка запихнуть всё в панель деталей.
Но я бы не начинал сразу с полноценного менеджера файлов и глобальной индексации всех дисков.
Это быстро превращается в отдельный продукт.

Разумная первая версия — окно:

```
File                  Used in       Expected path       Status
--------------------------------------------------------------
vocal_take_07.wav     Vocal 1       Samples/Vocals      Missing
bass_loop.wav         Bass          ../../Loops         Missing
```

Кнопки: Search in folder..., Search in project folders, Show expected path,
Open containing folder, Copy report, Rescan.

То есть первая версия может быть диагностической, без автоматического изменения `.als`.

### Индексация файлов

пользователь выбирает папки для поиска; менеджер сканирует только их; сохраняет индекс имён,
размеров и дат; глубокий анализ запускается только по запросу; индекс обновляется при
необходимости.

Например, пользователь добавил `E:\Samples`, `F:\Old Projects`, `G:\Backup`. Менеджер не обязан
каждый запуск заново проходить несколько терабайт. Достаточно кэшировать `имя → путь, размер,
дата изменения`. Хэши считать только у кандидатов одинакового размера.

### Поиск похожего аудио

Две разные задачи, и путать их нельзя.

**Точное восстановление.** Файл найден по имени, расширению, размеру, пути, возможно
длительности. Это относительно безопасно.

**Замена на похожий файл.** Это уже не восстановление, а творческая подмена: заменить
потерянный kick на похожий kick. Автоматически делать такое опасно. Для первой версии — только
показывать кандидатов:

```
Possible matches:
97%  kick_07.wav
82%  kick_07_new.wav
64%  kick_alt.wav
```

А саму замену оставлять пользователю или делать отдельным ручным действием. Сравнение может
идти по нормализованному имени, длительности, числу каналов, sample rate, размеру,
аудиосигнатуре.

Но я бы не начинал с автоматической замены внутри `.als`. Даже если ID клипов не обязательно
сломаются, `FileRef` может содержать дополнительные поля: хэш, размер, сведения об анализе.
Сначала нужно научиться надёжно создавать копию `.als`, менять ссылку, пересобирать gzip/XML и
проверять открытие в Live.


## Удаление плагина из сета — по-прежнему не стоит

**Сделано (по-другому):** помощник по восстановлению — `Ctrl R`, [src/RescueDialog.cs](src/RescueDialog.cs).
Он ничего из `.als` не удаляет: в КОПИИ сета подменяется только идентификатор плагина
(`Uid`/`UniqueId`), и Live показывает его как «плагин не найден», а всё остальное — узлы,
цепочки, автоматизация, блоб пресета — остаётся байт в байт. Диагноз обычно даже не требует
проб: журнал Live пишет `VST3: Going to restore: X` перед тем, как умереть внутри X.

Именно удалять плагин ИЗ сета не стоит и дальше. Плагин связан не только с одним узлом, но
может иметь состояние устройства, связи с цепочками, automation, ID, параметры, соседние узлы в
`DeviceChain`. Это хорошая тема на потом, но точно не ближайшая функция.
