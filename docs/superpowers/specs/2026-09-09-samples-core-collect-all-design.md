# Core сэмплов и Collect All

Дизайн первого куска большого обновления по сэмплам. Дата: 2026-09-09.

## Рамки

Обновление целиком состоит из трёх независимых фич на общем фундаменте:

| | что это | состояние |
|---|---|---|
| **Core** | модель зависимостей сета по сэмплам + патчер путей в `.als` | **эта спека** |
| **C. Collect All** | кнопка в инспекторе: собрать проект в переносимую папку | **эта спека** |
| **B. Rescue → Samples** | вторая вкладка в окне восстановления: замена потерянных сэмплов | отдельная спека позже |
| **A. Вкладка Samples** | какие паки используются, какие ни разу | отдельная спека позже |

Порядок выбран по зависимостям: Core нужен всем трём, Collect All — самый простой его
потребитель и заодно проверка того, что Core собран правильно. B переиспользует ровно тот же
патчер, отличается только источник нового пути. A единственная, кому нужен новый кеш на всю
библиотеку, и её лучше делать, когда модель уже устоялась.

## Что уже есть

Половина фундамента написана и работает — новое строится на ней, а не рядом.

- **`AlsFile`** читает `.als` (gzip поверх XML, потоково) и складывает каждый `FileRef` в
  `AlsInfo.Files` **в порядке документа**, с полями `RelativePath`, `AbsolutePath`,
  `LivePackName`, `RelativePathType`, `OriginalFileSize` и `Container` — именем узла-родителя.
  `FileRefInfo.IsSampleDependency` уже отделяет настоящий сэмпл клипа (`SampleRef`) от «памяти
  о происхождении» (`FilePresetRef`, `OriginalFileRef`, `AbletonDefaultPresetRef`).
- **`RefResolver`** разрешает ссылку по всем пяти корням Live (папка проекта, пак, User
  Library, Builtin, Core Library) и различает `Missing` и `MissingPack`. У него же кеш проб на
  время сканирования: на реальной библиотеке 96% проверок «есть ли такой файл» повторяют
  предыдущие.
- **`LiveEnvironment.Detect()`** читает `Library.cfg` всех установленных Live и отдаёт
  `Packs` — имя пака → папка. На машине разработки это 61 пак.
- **`AlsPatch`** уже умеет главное: потоково прочитать `.als`, накопить один узел, подменить в
  нём отдельные `Value` и записать всё остальное байт в байт в **новый** файл. Оригинал не
  трогается никогда. Патчер сэмплов — тот же приём на другом узле.

Чего нет: `index.cache` хранит только числа `MissingFiles` и `TotalRefs`, самих путей там нет.
Для Collect All это не нужно (разбор одного сета по требованию), для вкладки Samples
понадобится — но это уже спека A.

## Измерения на реальной библиотеке

Замерено на 25 сетах из `E:\Music\Ableton Projects\Series 2` — числа определяют дизайн, а не
иллюстрируют его.

```
FileRef по контейнерам           SampleRef по RelativePathType
  28631  SampleRef                 15829  тип 1  рядом с проектом, может уходить вверх
   4574  OriginalFileRef            5328  тип 5  из пака (LivePackName заполнен)
   3858  AbletonDefaultPresetRef    3759  тип 0  пустышка, ссылки нет
    718  FilePresetRef              2640  тип 3  внутри папки проекта
     54  MxPatchRef  (.amxd)         708  тип 6  User Library
                                     367  тип 7  Builtin / Core Library
```

Три вывода:

1. **Дедупликация обязательна.** 28 631 ссылка на сэмплы против примерно 1100 разных файлов:
   один сет ссылается на свою папку `Samples` сотнями клипов. Копировать нужно каждый файл по
   разу, а не по разу на ссылку.
2. **Паки нельзя собирать не спросив.** В этих сетах 17 паков, среди них Grand Piano (2873
   ссылки), Core Library (1848), Electric Keyboards (707). Собрать «всё» — положить в каждый
   проект по несколько гигабайт того, что есть у любого владельца Live.
3. **`.amxd` не особый случай.** Среди 54 ссылок `MxPatchRef` есть штатные устройства Live
   (`Devices/Audio Effects/LFO/Ableton Folder Info/LFO.amxd`, тип 7). Значит они подчиняются
   тем же категориям, что и сэмплы; отличается только папка назначения.

   Практический смысл этого — ровно тот, ради которого `.amxd` и просили собирать. Стороннее
   устройство лежит снаружи и попадает в `Elsewhere` или `UserLibrary`, то есть копируется по
   умолчанию: у получателя его может не быть. Штатный `LFO.amxd` попадает в `FactoryPack` и по
   умолчанию тоже копируется, но снимается той же галочкой, что и Grand Piano, — он есть у
   каждого, у кого есть Live.

## Формат: две вещи, которые молча ломают файл

Проверено на распакованном `flush.als` (553 974 строки):

- **Пути пишутся прямыми слэшами** и в `RelativePath`, и в `Path`, независимо от того, что это
  Windows. `RefResolver` уже приводит их к `\` на чтении; патчер обязан писать обратно `/`.
- **Значения экранируются по XML** — в файле 40 строк с `&amp;` и родственниками. `XmlReader`
  декодирует их на чтении, то есть в `FileRefInfo.RelativePath` лежит уже чистый текст. При
  записи их надо закодировать заново: папка «Drum & Bass», записанная как есть, порвёт
  документ. Экранируем `&`, `<`, `>`, `"`.

## Core, часть 1: `src/SampleScan.cs`

Зависимости одного сета по медиафайлам.

```csharp
public enum SampleOrigin
{
    InProject,     // уже в папке проекта — при сборке копируется всегда
    OtherProject,  // внутри чужой папки «* Project»
    UserLibrary,   // Documents\Ableton\User Library
    FactoryPack,   // установленный пак, Core Library и Builtin
    Elsewhere,     // просто где-то на диске
    Missing        // не нашли
}

public sealed class SampleDep
{
    public FileRefInfo Ref;            // одна из ссылок (для показа пути в UI)
    public ResolvedRef Resolved;       // где нашлась
    public SampleOrigin Origin;
    public string PackName = "";       // заполнено у FactoryPack
    public long Size;                  // с диска; 0, если не нашли
    public bool IsDevice;              // .amxd (MxPatchRef), а не сэмпл
    public readonly List<int> RefIndexes = new List<int>();   // номера FileRef в порядке документа
}

public static class SampleScan
{
    public static List<SampleDep> Of(AlsInfo info, string projectDir, LiveEnvironment env);
}
```

`AlsInfo` передаётся снаружи, а не читается внутри: тот же разбор нужен потом патчеру для
`expectedRefCount`, и читать файл дважды незачем.

**Отбор.** Берутся `FileRef` с контейнером `SampleRef` (сэмплы) и `MxPatchRef` (`.amxd`).
Остальные контейнеры — происхождение встроенного содержимого, файл для открытия сета не нужен;
это ровно то различие, которое `FileRefInfo.IsSampleDependency` уже проводит, `MxPatchRef`
добавляется к нему отдельным флагом `IsDevice`.

**Дедупликация.** Ключ — разрешённый путь без учёта регистра; у ненайденных — сырой путь
ссылки, чтобы десять клипов на один пропавший файл считались одной потерей. Все номера
`FileRef`, ведущие на один файл, копятся в `RefIndexes`: патчеру надо переписать их все.

**Классификация**, порядок проверок значим:

```
Resolved.Status == Missing | MissingPack           -> Missing
путь внутри projectDir                             -> InProject
RelativePathType 5, либо путь внутри env.Packs[*]  -> FactoryPack, PackName = имя пака
RelativePathType 7, либо путь внутри
        env.Builtin / env.CoreLibrary              -> FactoryPack, PackName = "Core Library"
RelativePathType 6, либо путь внутри
        env.UserLibrary                            -> UserLibrary
у пути есть предок с именем «* Project»            -> OtherProject
иначе                                              -> Elsewhere
```

`InProject` проверяется первым намеренно: проект, лежащий внутри User Library, — это всё равно
свой проект, и его сэмплы не «из библиотеки». Предок «* Project» ищется тем же правилом, что и
у `SetEntry.ProjectDir`, — не более четырёх уровней вверх.

**Размеры** снимаются `FileInfo` по каждому уникальному пути. На типичном сете это порядка
тысячи обращений: мгновенно на прогретом кеше, ощутимо на сетевом диске — поэтому зовущая
сторона делает это на фоновом потоке.

## Core, часть 2: `src/AlsSamplePatch.cs`

Копия сета с переписанными путями.

```csharp
public sealed class NewRef
{
    public string RelativePath = "";   // «Samples/Imported/kick.wav», прямые слэши
    public string AbsolutePath = "";   // полный путь в собранной папке, прямые слэши
    public int RelativePathType = 3;
    public bool ClearPack = true;      // обнулить LivePackName и LivePackId
}

public static class AlsSamplePatch
{
    /// <summary>
    /// Пишет в dst копию src, где у перечисленных FileRef заменены пути. Возвращает
    /// число тронутых узлов. При несовпадении числа FileRef с expectedRefCount
    /// удаляет dst и бросает исключение.
    /// </summary>
    public static int Rewrite(string src, string dst,
                              Dictionary<int, NewRef> byIndex, int expectedRefCount);
}
```

**Как узел адресуется.** В тексте `<FileRef>` не отличить от соседнего по содержимому: путь у
сэмпла клипа и у памяти о происхождении бывает буквально один и тот же. Поэтому узлы
сопоставляются **по номеру в порядке документа**. `AlsFile` уже обходит файл и складывает
`info.Files` по порядку, значит i-я запись в списке — это i-й `<FileRef>` в тексте. Патчер
считает открывающие теги и правит те, чей номер есть в словаре.

Так логика «какой это контейнер» не дублируется во втором месте. Разъехавшись, два разбора
переписали бы не ту ссылку, которую показали, — та же причина, по которой `AlsPatch` считает
идентификатор плагина тем же кодом, что и `AlsFile`.

**Самозакрывающиеся `<FileRef />` пропускают оба.** `AlsFile` создаёт `FileRefInfo` только при
`!IsEmptyElement`; патчер так же не увеличивает счётчик, если в теге перед `>` стоит `/`.

**Страховка.** Досчитав файл до конца, патчер сверяет число узлов с `expectedRefCount`. Не
сошлось — `dst` удаляется, правка не применяется, зовущая сторона получает исключение. Записать
неверный путь в ссылку на сэмпл хуже, чем не записать ничего: сет откроется, но зазвучит не
тем.

**Что меняется внутри узла:** `RelativePathType`, `RelativePath`, `Path`, а при `ClearPack` —
`LivePackName` и `LivePackId` в пустую строку. Значения экранируются по XML, слэши прямые. Всё
остальное — `Type`, `OriginalFileSize`, `OriginalCrc` — не трогается: размер и контрольная
сумма относятся к тому же файлу, он просто переехал.

**Механика** взята у `AlsPatch` целиком: `LineReader` с сохранением концов строк, накопление
узла в `StringBuilder`, `ReplaceAll` по тегу, gzip→gzip, `UTF8Encoding(false)` без BOM.
Оригинал не открывается на запись ни на одном пути кода.

## C. Collect All

### Логика: `src/CollectAll.cs`

Без UI, по образцу `RescueSession`.

```csharp
public sealed class CollectOptions
{
    public bool FromElsewhere = true;
    public bool FromOtherProjects = true;
    public bool FromUserLibrary = true;
    public bool FromFactoryPacks = true;
}

public sealed class CollectPlan
{
    public string TargetDir;                 // <Проект>\Collected\<имя сета>[ N]
    public List<SampleDep> Copy;             // что копируем, с учётом галочек
    public List<SampleDep> Skipped;          // отключено галочкой
    public List<SampleDep> NotFound;         // скопировать нечем
    public long TotalBytes;
    public long FreeBytes;                   // на диске назначения
    public Dictionary<int, NewRef> Rewrites; // для AlsSamplePatch
}

public static class CollectAll
{
    public static CollectPlan Plan(SetEntry set, List<SampleDep> deps, CollectOptions opt);
    public static void Run(CollectPlan plan, SetEntry set, AlsInfo info,
                           Action<int,int,string> progress, CancellationToken cancel);
}
```

Разделение на `Plan` и `Run` нужно окну: план считается до показа галочек и пересчитывается на
каждый щелчок, а `Run` уже только копирует.

### Что получается на диске

```
<Проект>\Collected\<имя сета>\
    <имя сета>.als             переписанная копия
    Ableton Project Info\      копия оригинальной; без неё Live не считает папку проектом
    Samples\
        Imported\              всё внешнее, плоско — как у штатного Collect All and Save
        Processed\ Recorded\   то, что было в проекте, со своим прежним путём
    Devices\                   .amxd
```

**Внутрипроектные ссылки не переписываются вообще.** Путь `Samples/Processed/x.wav` в копии
верен как есть, потому что структуру папки проекта мы повторяем. Переписываются только внешние:
на `Samples/Imported/…` (или `Devices/…` у `.amxd`), с `RelativePathType = 3` и пустым
`LivePackName`.

**Столкновения имён** в `Imported` разводятся суффиксом ` 2`, ` 3`. Сверка по источнику: один и
тот же файл, на который ссылаются двадцать клипов, копируется один раз (это и есть дедупликация
из `SampleScan`), а два разных `kick.wav` из разных паков получают разные имена.

**`Ableton Project Info`** копируется из оригинала. Нет её (сет лежит вне папки проекта) —
создаётся пустая: Live дописывает туда своё сама при первом сохранении.

**Повторный запуск** не перезаписывает: `Collected\<имя> 2\`. Ничего чужого мы не удаляем ни
при каких обстоятельствах.

### Окно: `src/CollectDialog.cs`

Одно окно, два состояния, как у `RescueDialog`.

**Состояние 1 — выбор.** Пока `SampleScan` считает размеры на фоновом потоке, показывается
«counting…». Дальше четыре пункта штатного диалога Live, каждый с числом файлов и весом:

```
Specify which used media files are to be copied into the project.

  [Yes]  Files from elsewhere            312 files    1.4 GB
  [Yes]  Files from other Projects        18 files    240 MB
  [Yes]  Files from User Library          41 files     96 MB
  [Yes]  Files from Factory Packs        740 files    5.8 GB

  In project (always copied)             204 files    810 MB
  Not found — left as they are             3 files
  ─────────────────────────────────────────────────────────
  Will copy 1315 files, 8.3 GB          Free on E: 240 GB
```

Пункты — ровно те же четыре, что у Live, по умолчанию все Yes, выбор запоминается в
`settings.cfg`. Сверх Live добавлены числа: 8.3 ГБ видно **до** нажатия OK, а не после. Не
влезает на диск — OK заблокирован.

**Состояние 2 — копирование.** Полоса, текущий файл, Cancel. Отмена удаляет собранную папку
целиком: её создал этот запуск, чужого там нет. Порядок операций — сначала все файлы, `.als`
пишется последним, чтобы прерванная сборка не оставила сет, который выглядит готовым.

По окончании — тост с числами и «показать в проводнике».

## Ошибки и краевые случаи

| ситуация | поведение |
|---|---|
| сэмпл не найден | скопировать нечем, ссылка остаётся как была; число таких — в отчёте |
| `.als` не разбирается | окно не открывается, тост с ошибкой |
| нет места на диске | OK заблокирован, видно сколько нужно и сколько есть |
| отмена в середине | собранная папка удаляется целиком |
| `Collected\<имя>` занята | берётся `<имя> 2`, `<имя> 3` |
| файл занят другим процессом | пропускается, попадает в отчёт, сборка продолжается |
| путь длиннее 260 символов | пропускается, попадает в отчёт (плоский `Imported` делает это редкостью) |
| число `FileRef` разошлось | `.als` не пишется, сборка объявляется неудачной |

## Проверка

`tools\SampleTest.cs` — консольный стенд рядом с существующим `RescueTest`, собирается тем же
`tools\build-rescue-test.cmd`, в `bin` не попадает.

```
SampleTest.exe scan  <корень>     разбивка по категориям на N сетах, сверка сумм
SampleTest.exe patch <set.als>    круг: переписать пути -> прочитать AlsFile -> сверить
```

Проверка `patch` — главная: она читает результат тем же `AlsFile`, что и весь остальной код, и
утверждает, что поменялись ровно заказанные `FileRef` и ровно заказанными значениями, а все
прочие поля всех прочих ссылок остались прежними. Это ровно тот инвариант, ради которого
патчер вообще устроен через номера узлов.

## Что осознанно не делается

- **Не трогается оригинал.** Ни Collect All, ни что-либо ещё из этой спеки не открывает
  исходный `.als` на запись. Штатный Collect All and Save в Live переписывает текущий проект на
  месте — здесь это сознательно не повторяется, потому что весь остальной Alive построен на
  обратном обещании.
- **Нет своей вкладки и своего кеша.** Collect All работает по одному выбранному сету и разбирает
  его по требованию. Кеш путей на всю библиотеку появится в спеке A, когда станет ясно, какие
  поля вкладке Samples действительно нужны.
- **Live 9 и старше не поддерживается.** Там `RelativePath` — это дерево
  `<RelativePathElement Dir="…"/>`, а не одно значение; `AlsFile` его и сейчас не читает.
  Отдельной поддержки не добавляется, такие ссылки просто выглядят пустыми.
- **Нет архивации в zip.** Собранная папка — обычная папка; упаковать её человек может сам.
